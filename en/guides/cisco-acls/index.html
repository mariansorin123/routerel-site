Cisco ACLs Explained: Standard, Extended, Wildcard Masks and Configuration

The Routerel team· Updated: November 9, 2026· 16 min read

ACLs look simple: a list of permit and deny rules. In practice, most mistakes come from three places: the wildcard mask, the order of the rules, and the direction you apply the list in. This guide works through each of them using one topology from start to finish.

You'll see what an ACL actually filters, the different types (standard, extended, numbered, named), wildcard masks with a quick method, the implicit deny, where and in which direction to apply a list, full Cisco IOS configuration, editing with sequence numbers, locking down SSH access and verifying everything with hit counters. It ends with the most common mistakes and practice questions with answers.

In the Networking Academy CCNA v8 courses, IPv4 ACLs are covered in CCNA 3 · CEN. On the 200-301 exam they sit in the security topics, both as theory and as configuration and troubleshooting questions.

The lab topology

Every example uses the network below. It's worth sketching it once on paper so you can follow where each ACL goes.

  • R1 has two LANs: Sales (G0/0/0) and Accounting (G0/0/1). Inside Accounting, addresses .16–.31 (192.168.20.16/28) belong to the IT team.
  • R2 has the server network on G0/0/0.
  • R1 and R2 are connected by a /30 serial link. Routing is already in place, so every network can reach every other one.

What an ACL filters

An ACL (access control list) is an ordered list of rules. Each rule, called an ACE (access control entry), says permit or deny for packets that match it. The router compares each packet against the list and decides whether to forward it or drop it.

Depending on its type, an ACL can match on:

  • the source IP address;
  • the destination IP address;
  • the protocol in the IP header (TCP, UDP, ICMP, OSPF, GRE and others);
  • the TCP or UDP source and destination ports;
  • a few extra details, such as the ICMP message type or whether a TCP connection is already established.

An ACL does not look at MAC addresses (other features handle that), and it knows nothing about applications beyond port numbers. To an ACL, "web" means TCP 80 or 443, not a particular website.

Filtering isn't the only job ACLs do. The same syntax is used to identify traffic for other features: which addresses NAT translates (see the NAT and PAT guide), which traffic goes into a VPN tunnel, which routes a route filter lets through. This guide focuses on filtering.

ACL types

Standard vs. extended

swipe

Standard ACL Extended ACL
What it checks source IP address only protocol, source, destination, ports
Precision coarse ("everything from network X") fine-grained ("only HTTPS from X to server Y")
Usual placement close to the destination close to the source
Sample rule permit 192.168.10.0 0.0.0.255 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 443

Numbered vs. named

A numbered ACL is identified by a number, and the number range also tells IOS the type:

swipe

Range Type
1–99 and 1300–1999 standard
100–199 and 2000–2699 extended

A named ACL gets a name you choose, such as SALES-IN, and you declare its type explicitly (standard or extended). A name is far easier to understand six months later, and editing is more convenient. Use names in new configurations.

On modern IOS the difference is mostly cosmetic: you can edit a numbered ACL with sequence numbers too, by entering it with ip access-list standard 10.

Wildcard masks

ACLs don't use subnet masks. They use wildcard masks, and the rule works bit by bit:

  • a 0 bit in the wildcard means the address bit must match;
  • a 1 bit means the bit doesn't matter.

In practice, a wildcard is the inverse of a subnet mask: wherever the mask has a 1, the wildcard has a 0, and the other way round.

The quick method: 255 minus the mask

For a normal subnet, subtract each mask octet from 255:

Mask       255.255.255.192
           255-255 . 255-255 . 255-255 . 255-192
Wildcard     0     .   0     .   0     .   63      → 0.0.0.63

Watch out for the trap mentioned in the subnetting guide: the block size (magic number) is 256 minus the mask, but the wildcard is 255 minus the mask. They're linked: in the interesting octet, the wildcard is always the block size minus 1. A /26 has a block size of 64, so its wildcard is 63.

swipe

Network Mask Wildcard Matches
192.168.10.0/24 255.255.255.0 0.0.0.255 .0 – .255
192.168.20.16/28 255.255.255.240 0.0.0.15 .16 – .31
10.1.1.0/30 255.255.255.252 0.0.0.3 .0 – .3
172.16.32.0/20 255.255.240.0 0.0.15.255 172.16.32.0 – 172.16.47.255
10.0.0.0/8 255.0.0.0 0.255.255.255 anything starting with 10.

To check your work, the subnet calculator shows the wildcard mask for any address and prefix. To see the individual bits, use the binary converter.

The host and any keywords

Two wildcards come up so often that they have shortcuts:

swipe

You type Same as Meaning
host 172.16.50.10 172.16.50.10 0.0.0.0 exactly that address
any 0.0.0.0 255.255.255.255 any address

In a standard ACL, if you type an address with no wildcard (permit 192.168.10.50), IOS assumes 0.0.0.0, which means a single host. In an extended ACL, you always have to spell out both source and destination: address plus wildcard, host, or any.

A wildcard that isn't a subnet

A wildcard doesn't have to be the inverse of a real subnet mask. 192.168.10.1 0.0.0.254 requires the last bit to be 1 and ignores the rest of the last octet, so it matches every odd address in 192.168.10.0/24. It rarely shows up on the exam, but it's a good test of whether you really understand the bit-level rule.

How the router reads an ACL

Top down, first match wins

The router compares the packet against the rules in order, top to bottom. At the first rule that matches, it applies that rule's action (permit or deny) and stops. Nothing further down the list matters for that packet.

Two writing rules follow from this:

  1. Specific rules at the top, general ones at the bottom. If deny 192.168.10.0 0.0.0.255 comes before permit host 192.168.10.50, host .50 never reaches its rule.
  2. Order matters as much as content. The same rules in a different order can do the exact opposite.

The implicit deny

Every ACL ends with a rule you never see in the configuration:

  • standard ACL: deny any;
  • extended ACL: deny ip any any.

The consequence: an ACL needs at least one permit, or it blocks everything. If you only want to stop one network and let the rest through, you need permit any (or permit ip any any) at the end.

Some admins write an explicit deny any log at the end. The effect is the same, but a visible rule has a hit counter and can send log messages, so you can see what's being blocked.

Good to know: if you apply an ACL that doesn't exist to an interface (a typo in the name, for example), IOS lets all traffic through. There's no error, just protection that isn't working. Always check with show ip interface.

Where and in which direction to apply an ACL

Inbound or outbound

Direction is always seen from the router's point of view, on the interface you pick:

  • in (inbound): the packet is checked as it enters the interface, before routing. If it's denied, the router never even looks up a route.
  • out (outbound): the packet is checked as it leaves the interface, after the router has decided where to send it.

An outbound ACL does not filter packets the router generates itself (a ping started from its own CLI, for example). An inbound ACL, on the other hand, also filters traffic addressed to the router, including routing protocols and DHCP requests, a detail that breaks a lot of labs.

One ACL per interface, per direction, per protocol

An interface can have at most one IPv4 ACL inbound and one IPv4 ACL outbound (plus, separately, one of each for IPv6). Apply a second IPv4 ACL in the same direction and it silently replaces the first.

Standard near the destination, extended near the source

A standard ACL only knows the source. Say you want to keep Sales away from the servers and you put a standard ACL on R1, inbound from Sales: you've just cut Sales off from everything, including Accounting and the internet. That's why it goes near the destination, on the last interface before the protected network.

An extended ACL also knows the destination, so it can be precise even when placed next to the source. You put it near the source so unwanted traffic is dropped as early as possible, without crossing the serial link first.

swipe

Goal in our topology Type Router and interface Direction
Sales can't reach the servers (one exception) standard R2, G0/0/0 (toward servers) out
Sales reaches the servers only for web and DNS extended R1, G0/0/0 (from Sales) in
SSH to R1 only from the IT subnet standard R1, VTY lines in (access-class)

Configuring a numbered standard ACL

Requirement: the Sales network (192.168.10.0/24) must not reach the server network, with one exception: the sales manager's PC, 192.168.10.50. Everything else heading to the servers (from Accounting, for example) is allowed.

It's a standard ACL, so it goes near the destination: on R2, outbound toward the servers.

R2(config)# access-list 10 remark Sales blocked from servers, except manager PC
R2(config)# access-list 10 permit host 192.168.10.50
R2(config)# access-list 10 deny 192.168.10.0 0.0.0.255
R2(config)# access-list 10 permit any
R2(config)# interface GigabitEthernet0/0/0
R2(config-if)# ip access-group 10 out

Line by line:

  • remark is just a comment. It filters nothing, but future you will be grateful for it.
  • permit host 192.168.10.50 comes first because it's the most specific. Put it second and the network-wide deny would catch it.
  • deny 192.168.10.0 0.0.0.255 blocks the rest of Sales.
  • permit any lets everything else through. Without it, the implicit deny would also block Accounting and any other traffic toward the servers.

Configuring a named standard ACL for VTY access

Requirement: SSH into R1 is allowed only from the IT stations, 192.168.20.16/28.

This time you don't apply the ACL to an interface but to the VTY lines (Telnet and SSH sessions), using access-class. That protects the router no matter which interface the connection arrives on.

R1(config)# ip access-list standard ADMIN-SSH
R1(config-std-nacl)# remark Only IT stations may manage this router
R1(config-std-nacl)# permit 192.168.20.16 0.0.0.15
R1(config-std-nacl)# deny any log
R1(config-std-nacl)# exit
R1(config)# line vty 0 4
R1(config-line)# access-class ADMIN-SSH in
R1(config-line)# transport input ssh

Keep in mind:

  • interfaces use ip access-group; VTY lines use access-class;
  • apply access-class to every VTY line on the device (check show running-config for a line vty 5 15 block too), or a connection can land on an unprotected line;
  • deny any log is optional, but it records rejected attempts in the log;
  • for the SSH setup itself (domain name, RSA keys, local users), see the Cisco IOS commands cheat sheet.

Configuring a named extended ACL with TCP and UDP ports

Requirement: Sales may use only two things on the server network: the internal website (172.16.50.10, HTTP and HTTPS) and DNS (172.16.50.53). They may also ping the server network for troubleshooting. All other traffic from Sales to the servers is blocked, while Sales traffic to other destinations (Accounting, the internet) is allowed.

It's an extended ACL, so it goes near the source: on R1, inbound from Sales. Treat this as a separate scenario from ACL 10: if that one were still applied on R2, it would keep blocking Sales traffic to the servers (except the manager's PC), including the web access allowed here.

The syntax of an extended rule:

permit|deny  protocol  source wildcard [port]  destination wildcard [port]  [options]

The configuration:

R1(config)# ip access-list extended SALES-IN
R1(config-ext-nacl)# remark Sales to servers: web, DNS and ping only
R1(config-ext-nacl)# permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 80
R1(config-ext-nacl)# permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 443
R1(config-ext-nacl)# permit udp 192.168.10.0 0.0.0.255 host 172.16.50.53 eq 53
R1(config-ext-nacl)# permit icmp 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255 echo
R1(config-ext-nacl)# deny ip 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255
R1(config-ext-nacl)# permit ip 192.168.10.0 0.0.0.255 any
R1(config-ext-nacl)# exit
R1(config)# interface GigabitEthernet0/0/0
R1(config-if)# ip access-group SALES-IN in

A few notes:

  • The port goes right after the address it belongs to. host 172.16.50.10 eq 443 means "destination 172.16.50.10, destination port 443". The client uses a random source port, so you don't filter on that.
  • DNS mostly uses UDP 53. It also uses TCP 53 for zone transfers and large responses; add a TCP rule if you need those.
  • echo matches only ping requests. The replies (echo-reply) return toward Sales through G0/0/0 outbound, where there's no ACL, so they get through.
  • The last rule only permits sources inside 192.168.10.0/24. A packet with a spoofed source address gets dropped by the implicit deny, which is a small security bonus.
  • Besides eq, you can use neq, lt, gt and range (for example range 20 21). IOS also accepts names for well-known ports: www (80), domain (53), telnet (23), smtp (25), ftp (21).

Good to know: the inbound ACL on G0/0/0 also filters traffic addressed to R1 itself. If R1 were the DHCP server for Sales, DHCP requests (source 0.0.0.0, destination 255.255.255.255) wouldn't match the last rule. The fix is a permit udp any any eq bootps rule placed above the others.

The established keyword

For TCP you can add established, which matches only segments with the ACK or RST bit set, meaning it never matches the opening segment of a new connection. Think of it as "only let in replies to connections started from inside". It's an old, stateless technique, and modern firewalls do the job far better, but for CCNA you need to know what the keyword does.

Editing named ACLs with sequence numbers

Every rule in an ACL has a sequence number. By default IOS numbers them in steps of 10, which leaves room in between.

New requirement: Sales also needs the file server, 172.16.50.20, on TCP 445. The rule has to sit before the deny at sequence 50, or it will never be reached.

R1(config)# ip access-list extended SALES-IN
R1(config-ext-nacl)# 45 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.20 eq 445
R1(config-ext-nacl)# end

To delete a single rule, use its sequence number. Say you no longer want to allow ping:

R1(config)# ip access-list extended SALES-IN
R1(config-ext-nacl)# no 40
R1(config-ext-nacl)# end

After many insertions the numbers can get crowded. Renumber them like this:

R1(config)# ip access-list resequence SALES-IN 10 10

The first value is the starting number, the second is the increment.

Good to know: for numbered ACLs, typing no access-list 10 deny 192.168.10.0 0.0.0.255 in global configuration mode deletes all of ACL 10, not just that line. To remove one entry from a numbered ACL, enter it with ip access-list standard 10 and use no <sequence number>.

Verification and hit counters

show access-lists

This command lists every ACL with its sequence numbers and, in parentheses, how many packets have matched each rule. Here's R1 after Sales has been working for a while (before the edits above):

R1# show access-lists
Standard IP access list ADMIN-SSH
    10 permit 192.168.20.16, wildcard bits 0.0.0.15 (6 matches)
    20 deny   any log (2 matches)
Extended IP access list SALES-IN
    10 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq www (1842 matches)
    20 permit tcp 192.168.10.0 0.0.0.255 host 172.16.50.10 eq 443 (5127 matches)
    30 permit udp 192.168.10.0 0.0.0.255 host 172.16.50.53 eq domain (633 matches)
    40 permit icmp 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255 echo (12 matches)
    50 deny ip 192.168.10.0 0.0.0.255 172.16.50.0 0.0.0.255 (41 matches)
    60 permit ip 192.168.10.0 0.0.0.255 any (9310 matches)

How to read it:

  • IOS shows well-known ports by name: 80 becomes www, 53 becomes domain.
  • The 41 matches on line 50 are blocked attempts. If someone in Sales says "the file server is down", this tells you the traffic is reaching the router and being dropped on purpose.
  • A rule with 0 matches after a full day of traffic is suspicious: either it's pointless, or a rule above it shadows it and packets never get that far.
  • The implicit deny isn't listed, so it has no counter. That's one reason people add an explicit deny at the end.

To start a clean count before a test:

R1# clear access-list counters SALES-IN

For a single ACL, use show access-lists SALES-IN. There's also show ip access-lists, which shows only IPv4 ACLs.

show ip interface

show access-lists tells you what's in a list, but not where it's applied. For that:

R1# show ip interface GigabitEthernet0/0/0 | include access list
  Outgoing access list is not set
  Inbound  access list is SALES-IN

If this says not set even though you configured the ACL, you forgot ip access-group or applied it to a different interface. For VTY lines, check with show running-config | section line vty.

Common mistakes

swipe

Symptom Likely cause How to check and fix
The ACL has no effect at all not applied, applied to the wrong interface, or the name doesn't match show ip interface → ip access-group NAME in/out on the right interface
It blocks exactly the wrong traffic the direction is reversed (in instead of out) think from the router's view: is the packet entering or leaving that interface?
A permitted host is still blocked a broader deny sits above its rule show access-lists → its rule has 0 matches; move it up with a lower sequence number
Nothing works after applying it the ACL contains only deny rules add permit any or permit ip any any at the end
A standard ACL blocks too much it's placed near the source move it near the destination
A rule matches the wrong addresses you typed the subnet mask instead of the wildcard (255.255.255.0 vs 0.0.0.255) recalculate: 255 minus the mask
The web rule never matches the port is attached to the source, not the destination permit tcp SOURCE WILDCARD host SERVER eq 443
OSPF or DHCP breaks after an inbound ACL the implicit deny catches traffic addressed to the router explicitly permit the protocol (for example permit ospf any any)
You accidentally deleted the whole ACL no access-list N ... in global config edit entries through ip access-list and sequence numbers

A concrete example of the wildcard mistake: access-list 20 permit 192.168.10.0 255.255.255.0 does not permit 192.168.10.0/24. The wildcard 255.255.255.0 ignores the first three octets and requires the last one to be 0, so it matches addresses like 10.4.7.0 or 172.16.50.0, and almost nothing useful.

Practice questions

  1. What's the wildcard for 172.16.32.0/20, and which address range does it match?
  2. You apply an ACL to an interface that contains only access-list 5 deny 10.0.0.0 0.255.255.255. What traffic still gets through?
  3. Write a named extended ACL, NO-TELNET, that blocks Telnet from Accounting (192.168.20.0/24) to any destination and permits everything else. Which router, interface and direction do you apply it to?
  4. A colleague wrote:
    ip access-list standard TEST
 permit any
 deny host 192.168.10.99
    Is 192.168.10.99 blocked? Why?
  5. Using SALES-IN in its original form (lines 10–60, before the edits), what happens to a packet from 192.168.10.70 to 172.16.50.20, TCP 445? And to one from 192.168.10.70 to 192.168.20.40, TCP 445?
  6. You want only the 10.1.1.0/30 network (the inter-router link) to be able to open SSH sessions to R2. Write the configuration.
Answers

1. The mask is 255.255.240.0, so the wildcard is 0.0.15.255. It matches 172.16.32.0 – 172.16.47.255 (a block of 16 in the third octet, and 32 + 15 = 47).

2. Nothing. The rule denies 10.0.0.0/8, and the implicit deny drops everything else. It's missing a permit any at the end.

3.

R1(config)# ip access-list extended NO-TELNET
R1(config-ext-nacl)# deny tcp 192.168.20.0 0.0.0.255 any eq 23
R1(config-ext-nacl)# permit ip any any
R1(config-ext-nacl)# exit
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# ip access-group NO-TELNET in

It's an extended ACL, so it goes near the source: R1, G0/0/1 (the interface facing Accounting), in. You can write eq telnet instead of eq 23. Note that it also blocks Telnet to R1 itself from Accounting.

4. No. The first rule, permit any, matches every packet, so processing stops there and the deny is never reached. The correct order is deny host 192.168.10.99 first, then permit any.

5. The first packet doesn't match lines 10–40 (different server, different port), matches line 50 (deny ip from Sales to 172.16.50.0/24) and is dropped. The second one isn't headed for the server network, so it slips past line 50 and matches line 60: permitted.

6.

R2(config)# ip access-list standard SSH-FROM-R1
R2(config-std-nacl)# permit 10.1.1.0 0.0.0.3
R2(config-std-nacl)# exit
R2(config)# line vty 0 4
R2(config-line)# access-class SSH-FROM-R1 in
R2(config-line)# transport input ssh

The implicit deny takes care of everything else. Apply it to every VTY line R2 has.

The fastest way to learn this

  • Draw first, configure second. For every requirement, mark the router, interface and direction on the diagram. Half the mistakes disappear right there.
  • Walk an imaginary packet down every ACL, the way practice question 5 does. That's exactly what exam questions ask you to do.
  • Drill wildcards until they're automatic, the same way you drill subnetting. Block size minus 1 covers almost every case.
  • Use the counters. In a lab, generate traffic (a ping, a web page) and watch which line's counter goes up. You'll understand rule order better than from any table.
  • Connect ACLs to VLANs. In a network with several VLANs, ACLs usually sit on the gateway interfaces; see the VLANs and trunks guide.

Frequently asked questions

What is an ACL?

An ordered list of permit and deny rules that a router compares against each packet. The first rule that matches decides what happens to the packet, and if nothing matches, the implicit deny at the end drops it.

What is the difference between a standard and an extended ACL?

A standard ACL checks only the source IP address. An extended ACL can check the protocol, the source and destination addresses and the TCP or UDP ports, so it can block a single service to a single server.

Where do you place standard and extended ACLs?

Standard ACLs as close to the destination as possible, because they only know the source and would block too much near it. Extended ACLs as close to the source as possible, so unwanted traffic is dropped before it uses up links in the network.

How do I calculate a wildcard mask?

Subtract each octet of the mask from 255: 255.255.255.0 becomes 0.0.0.255, 255.255.255.192 becomes 0.0.0.63, 255.255.240.0 becomes 0.0.15.255. A 0 bit means "must match"; a 1 bit means "doesn't matter".

What is the implicit deny?

An invisible rule at the end of every ACL that drops everything: deny any in standard ACLs and deny ip any any in extended ones. An ACL with only deny statements effectively blocks all traffic on the interface where you apply it.

How many ACLs can I apply to an interface?

One per interface, per direction, per protocol: at most one IPv4 ACL inbound and one IPv4 ACL outbound, plus one of each for IPv6. A second IPv4 ACL in the same direction replaces the first.

How do I restrict SSH access to a router with an ACL?

Create a standard ACL that permits only your management addresses and apply it to the VTY lines with access-class NAME in. Interfaces use ip access-group; VTY lines use access-class. For where ACLs fit in the exam, see our guide to CCNA.
